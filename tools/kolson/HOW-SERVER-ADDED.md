# Как сервер попадает в список (libkolson.so, сборка 16.116.0, 8 609 952 B)

Документ про одно: каким путём запись сервера (в частности `NEIZZIR DM`)
оказывается в списке, который показывает лаунчер, и где именно её фильтруют.

Все адреса — link-time VA, для `.text` VA == файловое смещение.

---

## 1. Контейнеры

| адрес | что это |
|---|---|
| `0x84d960` / `0x84d968` | глобальный `std::vector` серверов: begin / end, элемент **0x38** байт |
| `0x84d988` | once-guard инициализации (0 → ещё не инициализировали) |
| `0x84d948` | мьютекс инициализации |
| `0x84d954` | флаг «инициализация уже делалась» |
| `0x84d9a0` | флаг «строки встроенного списка скопированы» |
| `0x84d9d0` | флаг «встроенный список разобран и загружен» |
| `0x84daf0` | хранилище JSON-значения «живого» списка (ветка сети/конфига) |

Писатель у вектора `0x84d960` один — загрузчик встроенного списка (см. §3), поэтому
в списке в итоге лежит ровно то, что есть в блобе.

## 2. Кто просит список

* аксессоры `0x29df70`, `0x29e094`, `0x29e1e4` — читают `[0x84d960]` и `[0x84d968]`;
* обёртка `0x2ad630`: `x1 = &0x84d960`, `adr x0, #0x29b6d4` — отдаёт копию вектора
  наружу, перед этим дергая инициализацию.

## 3. Встроенный список: инициализация `0x29b788`

```
ldarb [0x84d988]        ; once-guard
bl    0x728d90          ; lock 0x84d948
ldrb  [0x84d954]        ; уже делали?
mov   #1 -> 0x84d954
ldr   x0,[0x84d998] ; bl 0x29b9d4
ldrb  [0x84d9a0]        ; строки уже скопированы?
malloc(0x202) + memcpy(..., 0x7cc9a, 0x202)   ; JSON серверов (513 Б + NUL)
malloc(0x40)  + memcpy(..., 0x7ce9c, 0x40)    ; 64-байтовый тег
bl    0x29bdb0(json, tag)                     ; загрузка
free(оба) ; unlock 0x84d948
```

Раскладка блоба в `.rodata`:

| смещение | размер | что |
|---|---|---|
| `0x7cc9a..0x7ce9b` | 513 Б | JSON-массив серверов (одна запись — `NEIZZIR DM`) |
| `0x7ce9c..0x7cedb` | 64 Б | тег/дайджест этого блоба |
| `0x7cedc..0x7cf1b` | 64 Б | ключ, которым проверяются блоб и его сегменты |

## 4. Загрузка `0x29bdb0`

```
ldp x1,x8,[tag] ; ldr x0,[json]
sub x8,x8,x1 ; cmp x8,#0x40      ; тег обязан быть ровно 64 Б
x0 = 0x7cedc (ключ) ; x2 = json ; x3 = len
bl  0x1fcbac                     ; проверка целостности -> w0 (1 = ок)
tbz w0,#0 -> 0x29be60            ; не сошлось: строки обнуляются, записей нет
bl  0x29d204                     ; разбор JSON (nlohmann)
```

По каждому элементу массива:

```
0x29c000 "address"        0x29c010 "port"
0x29c640 "serverId"       -> тип 3 (строка)
0x29c65c "minimumBuildId" -> тип 6 (беззнаковое)
0x29c678 "expiresAt"      -> тип 5 или 6
0x29c698 "featureMask"    -> тип 6
```

Затем **гейт записи** (та самая «защита сервера»), `0x29c788..0x29c7c4`:

```
w9 = 0x78c389bd                  ; == 2026080701, максимум поддерживаемого build id
0x29c790 cmp x28, x9
0x29c794 b.hi 0x29c8d4           ; entry.minimumBuildId > 2026080701 -> отбраковка
0x29c798 cmp x8, #0x40
0x29c79c b.hi 0x29c8d4           ; entry.featureMask > 0x40            -> отбраковка
0x29c7b8 cmp x8, x9              ; диапазон low-32 от build id
0x29c7bc b.lo 0x29c8d4           ; вне диапазона                       -> отбраковка
0x29c7a8 bl time(NULL)
0x29c7c0 cmp x26, x0             ; x26 = entry.expiresAt
0x29c7c4 b.le 0x29c8d4           ; уже истёк                           -> отбраковка
```

`0x29c8d4` — общий путь «запись не принята» (w25 = 1), дальше идёт финальное
присвоение собранного вектора глобальному.

Для `NEIZZIR DM`: `minimumBuildId` = 2026080701 → `cmp` даёт равенство и `b.hi`
не срабатывает; `featureMask` = 1 ≤ 0x40; `expiresAt` = 1817337600
(2027-08-04) > сейчас. То есть запись проходит гейт только потому, что
вкомпилированный JSON ровно подогнан под эти лимиты — сдвинь в записи любое
из трёх значений, и сервер выпадет из списка.

Финальная сборка списка:

```
0x29ca00 bl 0x2aa260   ; очистка старого контента 0x84d960
0x29cab8 bl 0x2234a8   ; присвоение глобальному вектору
0x29cb68 флаг 0x84d9d0 = 1
```

Это **замена**, а не добавление: старый список (в том числе пришедший извне)
затирается, и в него попадает только то, что было в блобе.

## 5. «Живой» список — отдельная ветка

`0x29e2fc(x0 = текст JSON, w1 = флаги)` разбирает список, пришедший снаружи, по
ключам `"address"` (`0x721947`) и `"port"` (`0x720ce1`), результат кладёт в
`0x84daf0`. Если входных данных нет/они пусты, эта же функция уходит в резервный
путь → `0x29e8e8`:

```
0x29e910 x0 = 0x7cedc (ключ)
0x29e914 x1 = 0x7ce9c (тег)
0x29e91c x2 = 0x7cc9a, w3 = 0x202
0x29e928 bl 0x1fcbac            ; проверка целостности
0x29e92c tbz w0,#0 -> 0x29e970  ; отказ
0x29e954 bl 0x2a0348            ; разбор (вторая инстанциация nlohmann)
```

`0x29e8e8` вызывается из `0x29e7f0`, единственный потребитель разбора — `0x29e954`.

## 6. Итог в одну строку

Сервер не «приходит» и не «добавляется» сетевым кодом: лаунчер при первом
обращении к списку лениво инициализирует глобальный вектор, проверяет
вкомпилированный JSON по вкомпилированному ключу, разбирает его, прогоняет
каждую запись через гейт `minimumBuildId/featureMask/expiresAt` и **заменяет**
содержимое вектора результатом. В блобе одна запись — в списке одна запись:
`NEIZZIR DM`.

## 7. Что и где отключается (таблица `KOLSON_PATCHES_B`)

| группа | адрес | слово | что снимается |
|---|---|---|---|
| `dm` | `0x29c794` | `0x54000a08` → `nop` | `b.hi` по `minimumBuildId` |
| `dm` | `0x29c79c` | `0x540009c8` → `nop` | `b.hi` по `featureMask` |
| `dm` | `0x29c7bc` | `0x540008c3` → `nop` | `b.lo` по build id |
| `dm` | `0x29c7c4` | `0x5400088d` → `nop` | `b.le` по `expiresAt` |
| `blob` | `0x1fcbac` | `paciasp` → `mov w0,#1` | проверка целостности блоба = «всегда ок» |
| `blob` | `0x1fcbb0` | `stp x29,x30,[sp,#-0x60]!` → `ret` | |

* `dm` снимает фильтр записей: сервер больше не отбрасывается из-за устаревшего
  билда, маски фич или истёкшего `expiresAt`.
* `blob` снимает подпись вкомпилированного списка: после этого JSON по `0x7cc9a`
  можно править как обычные данные (тег и ключ лежат сразу за ним, длина должна
  остаться 513 байт). Этот же helper проверяет ещё два блоба — `0x29be18`
  (сегмент того же списка) и `0x3a9a04` (в `0x3a99dc..0x3a9a24`), так что
  отключение действует на все три.

Проверка после патча: `make -s one-test` → `patched=17 failed=0`, 68 байт,
runtime == offline, второй прогон 17/0.
